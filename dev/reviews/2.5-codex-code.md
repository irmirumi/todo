# 또박 2.5.0 코드 검토 — Codex

2026-10-29 · 기준 커밋 `066fce4` · 검토만 수행. `dev/src`, 버전, 배포 설정, 운영 데이터는 바꾸지 않았다. 줄 번호는 이 기준의 원본이다.

한 사람이 두 기기로 쓰는 앱에서 가장 중요한 것은 **작업한 내용이 늦게 도착한 저장 때문에 사라지지 않는 것**이다. 2.5.0의 방향은 좋다. 다만 고정 ID, 서버 스냅샷 확인, 필드 쓰기를 넣었다는 사실만으로 동시 저장이 안전해지지는 않는다. 자동 생성·휴지통 정리·편집 저장의 경계를 먼저 보강하는 편이 새 기능보다 가치가 크다.

## 먼저 볼 순서

| 순서 | 발견 | 심각도 | 근거 수준 |
|---|---|---|---|
| 1 | C1 자동 생성의 늦은 `set`이 완료·수정·휴지통 상태를 덮을 수 있음 | 데이터를 잃음 | 실제 함수로 쓰기 순서 모의 재현 |
| 2 | C2 오래된 휴지통 스냅샷으로 복원한 항목을 영구 삭제할 수 있음 | 데이터를 잃음 | 실제 함수로 쓰기 순서 모의 재현 |
| 3 | C3 편집하지 않은 필드까지 저장해 다른 기기의 편집을 덮음 | 데이터를 잃음 | 실제 편집 함수 모의 재현 |
| 4 | C4 첫 서버 스냅샷에서는 자동 추가를 건너뛸 수 있음 | 기능이 틀림 | 실제 app.js + 가짜 Firebase로 재현 |
| 5 | C5 백업·빠른 입력의 날짜/새 필드 검증, C8 복구 안내 | 기능이 틀림 / 데이터를 잃음 | 입력 재현·소스 확인 |

‘데이터를 잃음’은 조건이 맞으면 발생할 결과의 심각도다. 운영 계정에서 사고를 관측했다는 뜻은 아니다. 아래에서 **브라우저 재현**, **모의 재현**, **소스 확정**, **의심**을 구별한다.

## 확인한 문제

### C1. 자동 추가는 중복 문서 수를 막지만, 기존 내용 덮어쓰기를 막지 않는다

- **심각도:** 데이터를 잃음. **위치:** [ui.js:235](src/ui.js#L235) `autoAdd`, 1217–1222 `addFromTpl`; [app.js:25](src/pwa/app.js#L25) `setDoc`.
- **조건·결과:** 폰과 PC가 같은 ‘아직 생성되지 않음’ 스냅샷을 읽는다. 폰의 생성이 먼저 저장되고 주인이 완료 체크/메모 편집/휴지통 이동을 한다. PC의 지연된 생성 `setDoc`이 뒤에 도착하면 `done:false`를 포함한 원본 본문으로 교체한다. `deletedAt`도 없는 본문이므로 휴지통 이동을 되돌릴 수 있다. 동일 ID는 문서가 두 개 되는 문제만 막는다.
- **검증:** [races.mjs](tests/repro/races.mjs)가 실제 `autoAdd/addFromTpl`를 추출해 이 순서를 실행한다. 제목과 완료 상태가 초기값으로 돌아감을 assertion으로 확인했다. Firestore 두 클라이언트를 연결한 재현은 아니다.
- **추가 위험:** 생성과 `madeUntil` 갱신도 별개 비동기 쓰기다. 한쪽만 성공하는 실패 순서, 오래된 기기가 watermark를 뒤로 쓰는 순서를 검증해야 한다. 이 부분은 실제 실패 주입 미실시다.
- **방향:** 생성 여부 확인과 생성·watermark 갱신을 온라인 트랜잭션으로 묶는다. 이미 있으면 본문을 쓰지 않는다. 앱 재개 때 다시 시도 가능하게 하되 watermark는 감소시키지 않는다. 트랜잭션은 오프라인에서 실행되지 않으므로 일반 할 일 편집의 오프라인 저장과 자동 유지보수의 정책을 분리한다. 단순 `merge:true`로 바꾸면 `done:false` 덮어쓰기가 남는다.
- **수용 검사:** 두 클라이언트의 동시 생성/완료/휴지통 이동, 생성 거절 후 watermark 성공, 오프라인 자정 후 재접속. 기존 작업은 그대로 보존되어야 한다.

### C2. 휴지통 자동 비우기는 복원과 충돌하면 되돌릴 길이 없다

- **심각도:** 데이터를 잃음. **위치:** [ui.js:251](src/ui.js#L251) `purgeTrash`, 254 `daily`, 1582 `tick`.
- **조건·결과:** A가 30일 지난 항목을 읽고 삭제를 결정한 뒤 B가 복원한다. A의 조건 없는 `remove`가 나중에 실행되면 복원본을 영구 삭제한다. `races.mjs`에서 실제 purge 함수와 이 순서를 재현했다. 운영 재현은 아니다.
- `onData(meta.server)`만 보는 것 같지만 `tick()`과 반복 편집의 `setTimeout(daily,0)`도 `daily`를 호출한다. 네트워크가 끊겨도 `S.mode`는 live일 수 있다. **최신 서버 상태에서만 유지보수를 실행한다는 주석/HANDOFF의 보장이 모든 진입점에 적용되지 않는다.**
- **방향:** 삭제 직전에 트랜잭션으로 `deletedAt`이 여전히 같은 값이며 만료됐는지 확인한다. 연결이 없거나 서버 상태를 확인하지 못하면 정리를 미룬다. `dailyDone`은 성공 전에 확정하지 말고 실패 때 재시도 가능하게 한다. 하루 조금 늦게 지워지는 것이 복원본을 잃는 것보다 낫다.

### C3. 일반 편집의 ‘필드 저장’은 변경 필드만 저장하는 방식이 아니다

- **심각도:** 데이터를 잃음. **위치:** [ui.js:1173](src/ui.js#L1173) `commitEdit`, 특히 1191–1192. 반복/고정 편집은 `commitTpl:1197`, `commitEv:944`에도 같은 성격이 있다.
- **조건·결과:** PC가 메모 A인 편집 창을 열어 둔다. 폰이 메모 B로 저장한다. PC가 제목만 고쳐 저장하면 `next`에는 여전히 메모 A가 들어 있고, 제목·메모·날짜·시간·세부 항목 등을 전부 patch한다. 최신 `t`와 비교해 다르면 저장하는 검사는 충돌 방지가 아니다. [edge_cases.mjs](tests/repro/edge_cases.mjs)에서 실제 `commitEdit`에 최신 서버 항목과 오래된 편집 draft를 넣어 메모 A가 patch에 포함됨을 확인했다. 두 브라우저 UI 재현은 하지 않았다.
- **방향:** 편집을 열 때의 기준본과 draft를 비교해 사용자가 실제 바꾼 필드만 patch한다. 같은 필드를 양쪽이 고친 경우에만 충돌 처리한다. 세부 항목 배열은 별도 병합 정책이 필요하다. 취소/다시 열기 동작을 유지하면서 단계적으로 고칠 수 있다.

### C4. 첫 스냅샷의 순서 때문에 자동 추가·정리가 빠질 수 있다

- **심각도:** 기능이 틀림. **위치:** [app.js:68](src/pwa/app.js#L68), 75; [ui.js:254](src/ui.js#L254), 1644–1648.
- **조건·결과:** 첫 콜백이 바로 `server:true`일 때 `onData → daily` 시점의 mode는 loading이라 반환한다. 그 뒤 `onStatus('live')`는 daily를 실행하지 않는다. 추가 스냅샷/사용자 쓰기가 없으면 그날 자동 할 일이 생기지 않는다. 휴지통 정리도 같은 경로다.
- **검증:** [initial_auto.py](tests/repro/initial_auto.py)는 실제 app.js와 기존 fake_firebase를 사용한다. 첫 서버 스냅샷 뒤 0개, 똑같은 스냅샷을 다시 전달하면 오늘·내일 2개가 생긴다. 실제 SDK가 캐시 스냅샷을 먼저 주면 다음 서버 스냅샷에서 실행되므로 **항상 실패한다고 해석하면 안 된다**.
- **방향:** 연결 상태 전환과 서버 최신성 확인을 하나의 시작 절차로 정리한다. 단순히 live 전환 때 무조건 daily를 부르면 캐시/오프라인에서 C1·C2가 커진다. 캐시→서버, 서버만, pending→확정 순서를 각각 검사한다.

### C5. 백업 새 필드는 보존되지만, 유효성 검사는 충분하지 않다

- **심각도:** 기능이 틀림. 잘못된 `deletedAt`을 복원하면 데이터를 잃을 위험도 있다.
- **위치:** [ui.js:728](src/ui.js#L728) `clean`, 740–747, 751–785; [model.js:23](src/model.js#L23), 95–100.
- `postponed`는 양의 정수 1–999만 보존한다. `deletedAt`은 숫자라는 조건뿐이다. 음수는 진실값이므로 휴지통으로 분류되고 즉시 만료 정리 대상이 된다. `auto`는 정확한 false 외에는 켜짐이며 문자열 `"false"`도 켜진다. `madeUntil`은 날짜 모양만 맞으면 아주 먼 미래도 받아 이후 생성을 막는다.
- `DATE_RE/TIME_RE`는 모양 검사다. `2026-02-31`, `99:99`를 실제 날짜·시각으로 검증하지 않는다. 빠른 입력에서도 `parseQuick('2월31일 회의','2026-01-01')`가 `2026-02-31`을 반환함을 `races.mjs`로 확인했다. 일부 날짜 계산은 JS Date가 3월로 보정하고, 목록은 원래 문자열을 써서 화면·알림이 달라질 수 있다.
- **방향:** model에 왕복 검증 가능한 날짜/시간 validator를 둔다. 빠른 입력에서 잘못된 토큰은 제목으로 남기고 날짜를 만들지 않는다. 백업은 필드별 이상값과 항목 수를 확인 화면에 알리고, 삭제 시각·watermark처럼 상태를 파괴할 수 있는 값은 조용히 정규화하지 않는다. 빠진 필드의 구버전 기본값과 잘못된 타입을 구분한다.
- `edge_cases.mjs`에서 실제 `clean/cleanTpl`에 잘못된 날짜·시간·삭제 시각과 문자열 false를 넣어 위 수용 동작을 확인했다.
- 기존 B1(미리 확인한 백업과 실제 입력 불일치), B2(목록 한도 조용히 잘라냄)는 이미 수정되어 이번 테스트도 통과했다. 새 문제와 섞어서 재발한 것처럼 쓰지 않는다.

### C6. 400개 초과 정리는 오래된 예외를 없애고 동시 저장 보호도 해제한다

- **심각도:** 데이터를 잃음. **위치:** [ui.js:988](src/ui.js#L988) `ovr`, 1345–1350 `skips`.
- 평상시 `arrayUnion/arrayRemove`는 서로 다른 날짜의 쉼을 보존하고, `ovr.<날짜#slot>`은 다른 발생 항목을 보존한다. 날짜의 `-`, slot 구분 `#`은 점 경로의 구분자인 `.`이 아니므로 이 키 자체를 버그로 보지 않는다.
- 401개가 되면 오래된 키를 지우고 **전체 배열/맵을 교체**한다. A가 정리하는 동안 B가 다른 날을 바꾸면 그 변경이 빠질 수 있다. 동시 사용이 없어도 예전 ‘쉼’이 다시 일정으로 나타나거나 과거의 장소/시간이 원본으로 돌아간다. 단순 용량 정리가 아니라 기록 의미 변경이다. `edge_cases.mjs`로 실제 `commitEvDay`의 401번째 변경이 전체 맵 patch를 만들고 가장 오래된 키를 빼는 것을 확인했다.
- 같은 `ovr` 키 안의 장소와 시간을 양쪽에서 바꾸는 경우도 한 칸 전체 교체라 충돌한다. 이는 현재 보호 범위 밖이다.
- **방향:** 정리는 별도 트랜잭션/보관 구조로 분리하고, 기록 보존 기간을 명시한다. 한 사람에게 400개는 당장 급한 규모가 아닐 수 있어도 조용한 삭제를 안전한 방식이라고 문서화하지 않는다. 같은 키 내부 변경은 실제 바뀐 하위 필드만 쓰는 방법을 검토한다.

### C7. 알림 전송이 일시 실패해도 예약을 지운다

- **심각도:** 기능이 틀림. **위치:** [worker.js:105](src/worker/worker.js#L105), 213–227.
- `sendPush`는 네트워크 예외/일부 HTTP 실패를 `fail`로 반환한다. tick은 결과가 `fail`이어도 마지막에 예약을 DELETE한다. 다음 분 재시도가 없어 그 알림은 사라진다. `edge_cases.mjs`에서 실제 tick 함수에 sendPush=fail을 주입해 해당 예약 DELETE를 확인했다. 실제 푸시 장애나 D1 쓰기를 일으키지는 않았다.
- **방향:** 만료 구독(gone)과 일시 실패를 나누고 제한된 재시도를 둔다. 일부 기기는 성공했을 때 전체를 무조건 재전송하면 중복되므로 기기별 성공 또는 멱등 처리가 필요하다. 현재 tag만으로 모든 플랫폼의 중복 알림을 막는다고 가정하지 않는다. 추가 D1 쓰기도 계산한다.
- `now+20000`까지 미리 전송한 항목은 아직 미래라 직후 `/sync`에 다시 포함될 수 있다(173–179). 중복 가능성은 별도 Worker 시각 고정 테스트로 확인할 항목이다. 매분 크론의 지연과 일괄 처리 때문에 ‘정확히 n분 전’을 보장하는 구조도 아니다.

### C8. 설치 안내가 지금의 복구·배포 절차와 충돌한다

- **심각도:** 데이터를 잃음(접근 상실 위험), 기능이 틀림(배포 안내).
- **위치:** [pwa/README.md:133](src/pwa/README.md#L133)–145, 159–171.
- 비밀번호 분실 시 Auth 사용자를 삭제하고 다시 만들라고 한다. 같은 이메일이어도 UID가 바뀌어 기존 Firestore 경로에 접근하지 못할 수 있다. 데이터가 자동 삭제된다는 뜻은 아니지만 비개발자 주인이 복구하기 매우 어렵다. 로그인 화면에는 이미 재설정 메일 기능이 있다.
- 루트 파일 업로드와 Pages의 `Deploy from a branch` 안내는 Actions 배포로 바뀐 현재 구조와 반대다. HANDOFF가 이 설정 변경 시 빈 루트를 서비스할 위험을 명시한다.
- **방향:** 비밀번호는 기존 UID를 유지하는 재설정 메일로 안내하고, 현재 앱 이용/복구 안내와 개발자 설치 안내를 분리한다. 배포는 현재 Actions 절차로 정정한다. **이번 PR에서는 요청대로 해당 원본을 수정하지 않았다.**

### C9. 전체 검색의 200개 제한이 결과 수와 맞지 않는다

- **심각도:** 기능이 틀림. **위치:** [ui.js:361](src/ui.js#L361)–377 `drawAll`.
- 결과 수는 `res.length`, 렌더링은 `res.slice(0,200)`이다. 넓은 검색어로 201개 이상 찾으면 일부 결과에 도달할 방법/안내가 없다. 검색은 과거 완료 기록도 포함하므로 한 명이 오래 쓰면 가능한 조건이다. 소스 확인이며 201개 UI 재현은 하지 않았다.
- **방향:** ‘200개 표시’와 더 보기 또는 날짜 범위 좁히기를 제공한다. 가상 스크롤 프레임워크를 새로 도입할 이유는 없다.

## 의심되거나 실제 SDK·기기에서 더 확인해야 할 것

### S1. `failWrite(last)`가 무엇을 되돌리는지 명확하지 않다

- **심각도:** 기능이 틀림, 조건에 따라 후속 저장 충돌. [app.js:12](src/pwa/app.js#L12)–13, 62–75, 21.
- `last`는 서버 확정본만이 아니라 캐시/pending 스냅샷도 받는다. A 쓰기 거절 중 B 쓰기가 진행 중일 때 `onData(last)`를 다시 보내는 것은 ‘A만 취소’가 아니다. Firestore 자체의 로컬 롤백과 콜백 순서에 따라 B가 잠깐 사라지거나 거절한 A가 다시 보일 수 있다. **이 호출만으로 B가 서버에서 삭제된다고 단정하지 않는다.**
- `apply`가 unarchive 매핑을 성공 전에 제거하는 것도 실패 후 재시도 검사 대상이다. 복수 쓰기의 결과를 실패/성공 순서별로 관측해야 한다.
- **다음 검사:** emulator/실제 SDK 로컬 환경에서 A 거절+B 지연 성공, A 성공+B 거절, 묶음에서 꺼내기 거절 후 재편집. UI/store 호출 기록·`fromCache/hasPendingWrites`·확정 데이터를 따로 비교한다. 작업 ID를 가진 pending 상태 또는 SDK 스냅샷 중심으로 UI 상태를 정리하는 방향이 낫다.

### S2. IndexedDB·다중 탭·12.19.0 검증은 가짜 Firebase 통과로 대신할 수 없다

- **심각도:** 기능이 틀림 가능성. [app.js:49](src/pwa/app.js#L49)–54, 97–101.
- `persistentLocalCache + persistentMultipleTabManager` 선택은 두 탭 사용에 맞다. 하지만 초기화의 try/catch만으로 비동기 IndexedDB 장애까지 fallback된다고 보장할 수 없다. 저장 공간 부족, private mode, 탭 소유권 변경, 로그아웃 후 오프라인 재개를 테스트해야 한다.
- SDK 12.19.0의 실제 다운로드/릴리스 변경 검증은 못 했다. 이 환경의 gstatic 요청이 프록시 403으로 막혔고, 전체 테스트는 fake로 대체한다. **앱 SDK에 403이 난다는 관측은 아니다.** API 이름이 코드에 있다는 사실을 호환성 검증 완료라고 쓰지 않는다.
- 무료 Firestore emulator를 별도 CI/로컬 검사에 쓰면 트랜잭션·규칙·변환 연산은 검증 가능하다. iOS 저장소 수명/실제 네트워크는 여전히 실기기 몫이다.

### S3. 새 버전 교체는 좋아졌지만 다중 탭과 최초 오프라인을 구별해야 한다

- **심각도:** 기능이 틀림 가능성 / 나중에 비용이 됨. [sw.js:4](src/pwa/sw.js#L4)–30, [app.js:143](src/pwa/app.js#L143)–157.
- 기존 `test_offline.py`로 최초 worker 활성화, 설치한 shell의 오프라인 재열기, 새 버전 안내→새로고침→이전 shell 캐시 삭제가 통과했다. 이 테스트는 Firebase 설정을 비워 SDK를 로드하지 않는다.
- 처음 방문부터 오프라인인 상태는 캐시가 없으므로 열릴 수 없다. 첫 온라인 로드가 불완전해 SDK가 LIB에 없는 경우도 별개다. `app.js:94`는 로드 실패 때 5초 뒤 재로드한다. 이 상태의 복구 UX와 재로드 반복은 미검증이다.
- `clients.claim()`은 다른 열린 탭도 제어한다. 새로고침을 요청한 탭만 reload한다. 다른 탭의 기존 JS와 새 worker가 함께 있을 때의 지연 import/편집 지속은 미검증이다. 일괄 새로고침으로 초안을 날리는 방식은 피한다.
- activate는 `ttobak-` 접두어 필터 없이 다른 cache 이름도 지운다. 같은 origin의 다른 앱이 있다면 영향을 줄 수 있다. 현재 해당 앱 존재는 모른다. 삭제 대상을 또박 shell로 제한하면 비용이 작다.
- `ttobak-lib-1`은 버전이 바뀌어도 남고 pruning이 없다. 같은 URL을 방문할 때마다 계속 복제되는 것은 아니지만 Firebase 버전과 글꼴 URL이 쌓이면 장기적으로 증가한다. 전체 LIB를 매번 지우기보다 현재/직전 SDK와 사용 글꼴을 정리하는 정책을 둔다. 비동기 cache put의 수명도 `waitUntil` 또는 응답 promise 안에서 보장할지 검토한다.
- iOS 홈 화면의 설치/로그인 저장소 분리, 백그라운드 복귀, worker 대기 및 실제 push는 **실기기 미검증**이다.

### S4. 알림 목록 전체 교체도 두 기기의 순서를 고려해야 한다

- **심각도:** 기능이 틀림 가능성. [push.js:65](src/pwa/push.js#L65)–90, [worker.js:173](src/worker/worker.js#L173)–185.
- 기기별 최신 목록을 `/sync`가 전체 교체한다. 폰의 새 스냅샷 요청 뒤 PC의 오래된 요청이 늦게 완료되면 알림만 과거 상태가 될 수 있다. Firestore 문서는 그대로다. 요청 중복 방지 hash는 기기 내 최적화이지 전역 순서 보장이 아니다.
- **다음 검사:** 두 `/sync` 요청 역순 도착, 한 기기가 숨겨질 때 flush, pending snapshot으로 예약한 뒤 저장 거절. 서버 revision/수락 조건이 필요한지 결과를 보고 결정한다. 관측 전 대규모 서버 설계를 추가하지 않는다.

## 무료 한도: 보통 사용은 여유가 있지만 읽기와 D1 행 쓰기를 따로 본다

**실사용 계측이 아니라 계산 예시다.** 계산용 무료 기준은 Firestore 하루 읽기 50,000 / 쓰기 20,000 / 삭제 20,000, Worker 요청 100,000, D1 읽은 행 5,000,000 / 쓴 행 100,000이다. 현재 계정의 대시보드/최신 약관은 조회하지 않았다. 과금 전환 제안은 없다.

- 하루 새 할 일 10 + 완료 10 + 편집/이동 10 = 약 30문서 쓰기. 반복 3개가 매일 생성되면 워밍업 후 약 3개 생성+3개 watermark = 6쓰기. 최초 실행은 오늘·내일 최대 6생성+3watermark. 휴지통 만료 10개는 약 10삭제이며 묶음에 들어 있으면 실제 ops에 따라 update/여러 쓰기가 될 수 있다. archive의 읽기 절감과 이동 쓰기도 별도로 센다.
- 필드 단위 update는 필드 수만큼 과금되지 않고 보통 한 문서 쓰기다. 기존 한 번의 저장을 변환 연산으로 바꾼 것 자체가 쓰기 횟수를 폭증시키지는 않는다. 자동 추가/자동 정리는 새 작업을 만들므로 0회는 아니다. 두 기기가 같은 유지보수를 중복 실행하면 더 늘어난다.
- `listen`은 items 전체를 구독한다. **기기 2 × 하루 완전 재조회 4 × 500문서 = 4,000읽기** + 변경 수신 정도를 계산 예로 잡을 수 있다. 모든 재개가 완전 재조회인 것은 아니고 캐시/연결 시간에 따라 달라진다. 기록 묶기는 이 비용을 낮춘다. 실제 문서 수/재연결 횟수를 보지 않고 항상 무료 한도와 멀다고 보장하지 않는다.
- 크론은 하루 1,440번이다. 유휴 시에도 만료 DELETE+due SELECT를 실행한다. 이것을 ‘2,880행 쓰기’라고 세면 틀린다. D1은 처리한 행과 index 갱신을 봐야 한다. `rem_at`, PK의 UID prefix, `subs_uid`가 있어 전체 무제한 스캔 구조는 아니다. isolate 재시작 시 init 쿼리도 추가된다.
- `/sync`의 300개 전체 교체는 최대 약 300삭제+300삽입에 index 비용이 붙는다. 100회면 원본 행만 60,000, 200회면 120,000으로 D1 무료 쓰기 한도에 닿을 수 있다. 이는 스트레스 예시이며 주인의 실제 목록/빈도는 모른다. 보통 30개를 20회 보내면 원본 행 약 1,200이다. 1.2초 debounce와 hash가 이미 있어 유지해야 한다.
- 먼저 하루 sync 수·목록 길이·D1 rows_written을 관측하고, 필요하면 변경 항목만 보내거나 같은 확정 상태의 중복 sync를 합친다. 정확한 매분 알림을 포기하는 크론 축소나 유료 전환을 먼저 권하지 않는다.

## 작게 나누는 구조 개선 순서

1. **계약 먼저:** store의 확정/pending/실패·유지보수 호출 조건을 정의한다. C1–C4 재현을 회귀 검사로 만든다. 파일을 옮기기만 해서는 안전성이 좋아지지 않는다.
2. **유효성/명령 분리:** model의 실제 날짜 검증, import validator, 자동 추가/휴지통 정리의 ‘계획’ 계산을 DOM 없는 함수로 추출한다. 실행은 store가 담당한다.
