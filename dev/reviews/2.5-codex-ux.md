# 또박 2.5.0 사용성·디자인·문구 검토 — Codex

2026-10-29 · 기준 `066fce4` · 한 사람이 폰과 PC에서 매일 쓰는 앱이라는 기준으로 검토했다. 실제 사용자를 모집한 조사가 아니라, 합성 데이터로 과업을 수행한 전문가 검토다. 모든 제안은 무료 플랜 안에서 가능해야 한다. 앱 원본은 수정하지 않았다.

## 매일 쓰는 데 가장 큰 차이를 만들 다섯 가지

1. **반복 할 일의 자동 추가를 믿을 수 있게 만든다.** 반복/고정 일정을 합치기보다 ‘체크해서 끝내는 일’과 ‘시간을 차지하는 일정’을 구별한다. 자동 생성 시점과 앱을 닫아 둔 동안의 알림 한계를 정확히 보여 준다. 동시 저장 문제는 [코드 C1–C4](CODE-REVIEW-codex.md)부터 해결한다.
2. **날짜 이동·안 함·삭제의 결과와 복구 가능성을 맞춘다.** ‘넘기기’는 ‘날짜 옮기기’, 할 일 삭제는 ‘휴지통으로’가 더 직접적이다. 고정/반복 일정의 삭제는 현재 휴지통에 가지 않으므로 그 차이를 누르기 전에 알려야 한다.
3. **글자 크기보다 먼저 색 대비를 고친다.** 시간표 고정 일정의 흰 글자는 8색 모두 양 테마에서 일반 글자 권장 대비에 못 미친다. 밝은 테마의 보조 글자와 분홍 주요 버튼도 일부 미달이다. 시간표 글자 크기는 주인의 결정을 유지한다.
4. **놓치면 곤란한 안내를 화면에 남긴다.** 저장 실패·저장 안 된 편집·오전/오후 추정 수정은 2.4~5초 토스트에만 의존하지 않게 한다. 성공 알림은 지금처럼 짧게 둬도 된다.
5. **오늘 해야 할 일이 먼저 보이게 한다.** 폰에서는 밀린 일과 고정 일정 요약의 높이를 조절하고 ‘N번 미룸’은 상세로 옮기는 편을 권한다. 여백을 줄여 빽빽하게 만드는 방식은 피한다.

## 기능·사용성 판단

심각도 **높음**은 저장 신뢰·복구·읽기/조작에 영향을 주는 것, **중간**은 반복되는 마찰·오해, **낮음**은 국소적 다듬기다. 취향에 가까운 판단과 실제 동작 확인을 구별한다.

### U1. 반복 할 일과 고정 일정은 나눈 채로 차이를 더 분명히 한다 — 중간

**화면:** [반복 목록](ux-shots/390-light-week-tpls.png), [고정 일정 목록](ux-shots/390-light-week-evs.png), 시간표 빈칸의 종류 선택. `ui.js:713,876,1028–1030`.

두 개념의 차이는 반복 여부가 아니다. 분리수거는 매주 ‘했는지’를 남기는 일이고, 수업은 달력의 시간을 차지하는 일정이다. 완료·안 함·세부 할 일과, 장소·공휴일 쉼·여러 시간대라는 차이도 있다. 통합하면 사용자가 매번 완료 가능 여부와 발생 종류를 고르게 될 수 있다. 한 사람용 앱에 그런 범용 모델을 도입할 이득이 작다.

**방향:** 이름은 우선 유지하고 생성/관리 설명을 ‘요일마다 체크할 일’ / ‘체크하지 않는 정기 일정’으로 짧게 구별한다. 시간표 빈칸의 ‘할 일’ 아래에는 나중에 반복으로 등록할 수 있음을 필요할 때만 알려 준다. 체크할 필요가 없는 습관까지 할 일로 만들게 유도하지 않는다. 통합 필요 여부는 주인이 실제로 같은 것을 두 곳에 중복 등록하는지로 판단해야 하며 그 행동은 아직 관찰하지 못했다.

### U2. 자동 추가 기본 켬은 새 반복에는 적절하지만, 상태 문구가 계약을 흐린다 — 높음

**화면:** 달력의 흐린 줄, 반복 설정의 자동 추가 checkbox, 정보 창. `ui.js:232–249,260,713,844,1123–1124`.

자동 추가는 매번 ＋를 누르는 수고를 줄인다. 반면 ‘그날이 되면’은 앱을 안 열어도 발생/알림이 준비되는 것으로 읽힐 수 있다. 구현은 앱에서 오늘·내일만 생성한다. 아직 생성되지 않은 템플릿은 push 목록에도 없다. 이 차이는 일정을 믿고 앱을 닫는 매일의 사용에 중요하다.

‘자동 추가’는 동작 이름인지 예정 상태인지 모호하고, ‘추가 전’은 사용자가 해야 할 다음 행동을 말하지 않는다. 목록에는 자동/수동을 한눈에 비교할 표시도 부족하다.

**방향:** 자동 예정 칸은 ‘추가 예정’, 수동 칸은 ‘눌러서 추가’. 반복 목록 각 행에 ‘자동’/‘직접 추가’를 표시한다. 설명은 ‘앱을 열면 오늘·내일 할 일을 넣어요’처럼 현재 동작을 정확히 말하되, 실제 시작 순서 오류를 먼저 고친다. 이미 있는 모든 구버전 반복을 `auto` 없음=켬으로 바꾸는 것은 선택 변경이다. 새 항목 기본 켬은 유지하되 기존 항목은 주인과 한 번 목록을 확인하는 편이 낫다. 매번 확인 창을 추가하자는 뜻은 아니다.

오늘 목록에 자동 항목이 몇 개 들어오는 것 자체는 문제가 아니다. 원치 않는 반복을 쉽게 중지할 수 있고, 며칠 안 열었을 때 밀린 반복을 소급 생성하지 않는 현재 방침은 이 앱에 잘 맞는다.

### U3. 치우는 세 길은 필요하지만 ‘삭제’의 복구 규칙이 서로 다르다 — 높음

**화면:** [날짜 이동](ux-shots/390-dark-week-later.png), 할 일 편집, 고정/반복 편집, [휴지통](ux-shots/390-dark-week-trash.png). `ui.js:1006–1024,1165–1166,1341–1342,1404,1630–1635`.

| 의도 | 현재 결과 | 제안하는 표현 |
|---|---|---|
| 나중에 하겠다 | 같은 할 일의 날짜 이동 | 날짜 옮기기 |
| 이번 일은 하지 않겠다 | 안 함 기록으로 보관 | 안 함으로 남기기 |
| 목록에서 지우겠다 | 일반 할 일은 휴지통 30일 | 휴지통으로 |
| 반복 설정/고정 일정을 없애겠다 | 즉시 삭제, 잠깐 되돌리기만 가능 | 삭제 + 복구 범위 사전 안내 |

이 세 행동을 합칠 필요는 없다. 지금 날짜 이동 시트의 ‘언제로 옮길까요?’는 잘 썼다. 문제는 입구가 ‘넘기기’라 안 함까지 포함하는 뜻을 추론해야 하고, 같은 ‘삭제’가 서로 다른 복구를 제공한다는 것이다.

**방향:** 일반 할 일은 ‘휴지통으로’로 직접 표시하고, 영구 삭제는 작은 확인 단계에서 ‘휴지통에 남지 않아요’를 알린다. 자주 쓰는 일반 삭제에 확인 창을 늘릴 필요는 없다. 휴지통의 ‘정말 비우기’는 결과를 말하는 ‘모두 영구 삭제’가 낫다. 반복/고정까지 휴지통을 확장하는 것은 별도 구현 판단으로 남긴다.

### U4. ‘N번 미룸’은 상세 기록으로 두는 편이 낫다 — 중간·제품 판단

**화면:** 할 일의 메타 칩, 정보 창 `ui.js:281,810`.

다음 행동을 결정하려면 제목·날짜·시간·알림이 먼저다. 미룬 횟수는 이유를 알려주지 않으며 ‘네 번이나 미뤘다’는 평가처럼 읽힐 수 있다. 주인에게 실제로 부담을 줬다는 관찰은 아니고 **사용자 확인이 필요한 판단**이다. 이번 4회 미룬 예시에서는 시간과 같은 줄에서 주의를 나눴다.

**방향:** 카운터 저장과 상세의 ‘옮긴 횟수’는 유지하되 기본 목록 칩은 빼는 쪽을 권한다. 미루기 통계·등급·죄책감을 주는 색은 추가하지 않는다. 목록 표시 설정을 하나 더 만들기보다 주인과 한 번 사용 선호를 결정한다. 반복 항목을 다른 날로 옮겼을 때도 과한 반성 기록을 만들 필요가 없다.

### U5. 접힌 편집은 유지하고 시간 입력 뒤 알림 발견성을 보강한다 — 중간

**화면:** [접힘](ux-shots/390-light-empty-edit-folded.png) / [펼침](ux-shots/390-light-empty-edit-expanded.png). `ui.js:1134–1146`, `style.css:708`.

‘더 보기’보다 ‘알림 · 반복 · 세부 할 일 · 메모’를 직접 보여 주는 것은 좋다. 값이 있으면 자동 펼침도 적절하다. 다만 작은 회색 링크가 날짜·시간 아래에 붙어 시간까지 정한 사용자가 알림 기능을 못 보고 저장하기 쉽다. 네 기능이 한꺼번에 펼쳐져 다시 긴 편집창이 된다.

**방향:** 시간을 넣으면 가까운 곳에 ‘알림 없음’ 버튼을 보여 주고, 나머지는 지금처럼 접는다. 반복은 기존 할 일에서 등록하는 경로를 유지한다. 첫 실행에 여러 장의 설명/투어를 추가할 필요는 없다.

### U6. 한 줄 입력은 이미 발견할 수 있다. 추정 수정은 저장 전에 가능해야 한다 — 중간

**화면:** [내일 3시 회의 입력](ux-shots/390-light-empty-quick.png). `ui.js:88–94,134–139,298,323`.

빈 화면 안내와 placeholder에 문법 예가 있고, 입력 아래에 인식 결과가 나온다. ‘이런 문법이 있다는 걸 전혀 알 수 없다’는 평가는 맞지 않는다. 단 3시를 오후로 정한 근거는 주인이 모르며, 반대쪽으로 바꾸는 간단한 길은 저장 후 5초 토스트에 있다. 추정 때는 같은 토스트 자리를 써 다른 날의 ‘보기’ 동작도 빠진다.

**방향:** 미리보기의 ‘오후 3:00’을 눌러 오전/오후를 바로 바꾸게 한다. 저장 후에도 편집에서 바꿀 수 있는 길은 그대로 둔다. 문법 안내를 길게 늘리거나 매번 확인 창을 띄우기보다 실제 해석 결과를 조작 가능하게 하는 편이 빠르다. 잘못된 날짜가 해석되는 코드 C5도 함께 수정한다.

### U7. 폰 오늘 화면의 정보 순서는 ‘다음 할 일’을 늦게 보여 준다 — 중간

**화면:** [폰 오늘](ux-shots/390-light-week-day.png), [PC 오늘](ux-shots/1280-light-week-day.png). `ui.js:307–326`.

폰 예시에서는 상단 탭→주 달력→큰 날짜→완료율→밀린 일→고정 일정 3줄 다음에 첫 체크 항목이 나온다. 첫 할 일은 화면 아래쪽 약 600px 부근이다. 정보를 많이 넣어서 공간이 부족한 것이므로 글자·여백을 줄이는 것으로 풀지 않는다.

**방향:** 고정 일정은 가장 가까운 일정과 ‘오늘 일정 3개’ 펼침으로 요약하는 안을 먼저 비교한다. 밀린 일의 개수/진입점은 유지하되 매일 ‘모두 오늘로’가 가장 강한 제안이 되지 않게 한다. 처리 안 한 일을 일괄 오늘로 보내면 오늘의 계획이 더 흐려진다. 달력 전체를 지우거나 새 ‘집중 모드’ 탭을 만드는 것은 과하다. PC의 달력/내용 2열과 제한된 본문 폭은 읽기 편하므로 그대로 둬도 된다.

### U8. 탭·설정은 지금 정도가 적절하다 — 낮음

**화면:** [메뉴](ux-shots/390-light-week-menu.png), 시간표 아래 관리 링크. `markup.html:3–8`, `ui.js:545,675–686`.

달력/시간표/전체는 서로 다른 질문에 답한다. 전체 검색이 생겼고, 고정/반복 관리도 시간표 아래에서 갈 수 있어 이전 검토의 ‘메뉴에만 묻힘’은 완화됐다. 백업/복원/로그아웃이 주 화면에 없는 것도 적절하다.

**방향:** ‘전체’가 고정 일정까지 모두 검색한다는 오해를 줄이려면 검색 placeholder를 ‘할 일 검색’으로 유지한다(이미 그렇다). 검색 범위를 괜히 확대할 필요는 없다. 알림은 관리 메뉴보다 할 일의 시간 선택 근처에서 연결하는 U5가 더 효과적이다. 폰 한 손으로 상단 탭/⋯에 닿기 불편할 가능성은 있지만 실제 손 사용은 미검증이므로 하단 탭바 개편을 즉시 권하지 않는다.

### U9. 토스트가 잘 맞는 성공 알림과 남겨야 할 오류를 나눈다 — 높음

**화면:** 저장 실패, 편집 닫기, 추가·삭제 후 피드백. `ui.js:117–124,628,671,1561–1568`; `markup.html:16–17`.

일반 토스트는 2.4초, 행동이 있으면 5초다. 작은 성공 피드백에는 충분하지만 저장 실패와 초안 복구의 유일한 경로로는 짧다. 여러 조작을 하면 다음 메시지가 앞 메시지를 대체한다. 스크린리더용 role=status는 이미 있으므로 ‘알림 접근성이 전혀 없음’은 아니다.

**방향:** 저장 실패를 해당 항목/편집창에 남기고 재시도 또는 다시 열기를 제공한다. 초안은 다시 편집할 때 복구할 수 있게 한다. 서버 확인 전 ‘완료’처럼 보이는 순간과 실제 저장 완료를 구별한다. 일반 완료 체크마다 ‘저장됐어요’를 띄우는 등 성공 메시지는 늘리지 않는다.

## UI 디자인·접근성

### D1. 두 테마의 대비를 재조정한다 — 높음

**위치:** `style.css:5–8,14–17,190–191,548–549`. [밝은 고정 일정](ux-shots/1280-light-empty-first-timetable.png), [어두운 시간표](ux-shots/390-dark-week-week.png).

[contrast.py](tests/repro/contrast.py)로 현재 sRGB 토큰/`color-mix`를 계산했다. [계산 결과](ux-shots/contrast.json)는 이미지 픽셀 측정이 아니라 CSS 색 조합 계산이다. 일반 글자 4.5:1 기준으로 비교했다.

| 조합 | 밝음 | 어두움 | 판단 |
|---|---:|---:|---|
| 보조 글자 / 전체 배경 | 4.10 | 6.62 | 밝음 보강 |
| 보조 글자 / 움푹한 배경(sunk) | 3.85 | 5.36 | 밝음 보강 |
| 주요 버튼 글자 / 분홍 배경 | 4.10 | 6.36 | 밝음 보강 |
| 고정 일정 흰 제목 / c1–c8 혼합 배경 | 2.11–3.06 | 2.94–3.74 | 양쪽 보강 |

고정 일정은 `--cc 78% + surface 22%` 위에 흰 글자를 얹는다. 보조 시간·장소의 opacity .9는 대비를 더 낮춘다. **글자 크기를 유지하면서** 밝은 배경에는 짙은 잉크를 쓰거나, 고정 일정용 바탕 토큰을 더 짙게 만들 수 있다. 완료/쉼처럼 비활성 표현과 정상 활성 일정은 구별해서 검사한다.

### D2. 8색은 장식적 구별에는 충분하지만 색만 믿으면 안 된다 — 중간

폰/PC 양 테마에서 8색을 확인했다. c1(코랄)/c7(분홍), c3(초록)/c4(청록), c5(파랑)/c6(보라)는 작은 점으로 보면 가까운 쌍이다. 색각 시뮬레이터나 실사용자 검사를 한 것은 아니다. 카테고리 이름, 일정 제목, 체크 모양이 함께 있어 색만으로 내용을 전달하는 구조는 대체로 피했다.

분홍 c7이 카테고리 색으로 쓰이는 것은 주 강조색과 비슷해진다. HANDOFF의 ‘분홍은 오늘/주요 버튼’ 규칙은 **카테고리 팔레트의 c7 예외**를 명시하는 편이 현재 구현과 맞는다. 취향 차이로 주인이 익숙한 카테고리 색을 빼지는 않는다. 현재 시각 선·오늘 표시는 분홍의 일관된 용도다.

색 선택 버튼의 `aria-label="색 1"` 같은 이름은 색을 선택하는 데 충분한 의미가 없다(`ui.js:921`, 카테고리 색 버튼도 확인). ‘코랄’, ‘초록’ 등 이름과 선택 상태를 함께 읽게 한다. 8색을 더 늘리기보다 제목/아이콘의 보조 정보를 유지한다.

### D3. 기본 타이포·여백은 유지하고 예외만 정리한다 — 낮음

날짜 제목→카테고리→할 일→메타 정보의 단계가 보이며, 단일 글꼴·굵기 변화도 일관적이다. 날짜/요일과 정보 창, 소분류 태그는 baseline 정렬을 명시해 둔 점이 좋다(`style.css:336–339,481,666–670`). 둥근 상자의 한쪽 테두리를 새로 추가하거나 페이드를 넣을 이유가 없다.

반복 관리 행은 바깥 `.tplrow`가 center, 안쪽 `.nm`는 baseline이라 이름과 더 작은 `.when`의 글자선이 완전히 같지 않을 수 있다(`305,309,666`). [반복 목록](ux-shots/390-light-week-tpls.png)에서 이런 조합을 우선 비교하면 된다. 전역으로 모든 center를 baseline으로 바꾸면 아이콘/컨트롤까지 어긋나니 예외만 조정한다.

어두운 테마는 별도 잉크·분홍 글자색·카테고리 색이 있어 단순 반전이 아니다. 카드와 배경의 차이가 절제되어 있고 눈부심도 적다. D1의 고정 일정 흰 글자 조합이 남은 핵심이다. PC가 넓다고 할 일 카드를 여러 열로 늘려 읽는 순서를 복잡하게 만들지 않는다.

### D4. 작은 선택 칩과 시트 이름을 점검한다 — 중간

`style.css:136`의 일반 pill, `186`의 32px x, `233`의 작은 복원 버튼은 긴급하지 않지만 손가락 선택에는 작다. checkbox는 시각적으로 20–22px여도 pseudo-element로 약 44px 영역을 확보했고, 넘기기/시간표 필터도 확장 영역이 있다. 겉 크기만 보고 전부 터치 기준 미달이라고 판단하지 않았다. 작은 pill은 최소 24px 접근성 기준과 44px 사용성 권장을 혼동하지 않고, 촘촘한 요일·알림 선택부터 높이/간격을 개선한다.

`markup.html:16`의 dialog에는 접근 가능한 제목 연결이 없다. 시트마다 표시 제목을 `aria-labelledby`로 연결한다. 휴지통 여러 ‘복원’, 세부 항목 여러 ‘지우기’는 대상 이름을 포함한 접근 가능한 이름을 제공한다(`ui.js:1148,1634`). 아이콘 주요 버튼에는 이미 이름이 있는 곳이 많다. VoiceOver/TalkBack 실사용은 하지 않았으므로 포커스 이동과 읽기 순서는 후속 실기기 확인이 필요하다.

### D5. 시간표의 겹침과 지금 선은 유지한다 — 낮음

[겹침 화면](ux-shots/1280-dark-week-week.png)의 묶음 개수와 누르면 보는 목록은 일정이 겹칠 때 칸을 지나치게 좁히는 것보다 낫다. 지금 선은 선택한 오늘 칸의 맥락을 준다. 표시 시간 범위 밖에서 선이 없는 것은 정상 동작일 수 있다. 글자 크기는 요청대로 변경 제안에서 제외했다. 제목/장소를 다 넣기 어려울 때 상세로 넘기는 현행 방향도 유지한다. 시각 겹침과 실제 저장 시간이 같은지는 기존 tests 및 코드 문서의 날짜·시간 항목을 함께 본다.

## 문구 검토

소스 목록 도구로 **308개 위치의 문구 묶음**을 확인하고, `ui.js`, `markup.html`, `pwa/app.js`, `pwa/push.js`, `pwa/sw.js`, `worker/worker.js`, `pwa/README.md`를 함께 읽었다. 308개는 고유 문장 수나 실제 본 화면 수가 아니다. 동적 조합·접근성 이름·오류 분기까지 보되 모든 오류를 실제 서비스에서 발생시키지는 않았다.

앱의 해요체는 대체로 고르다. ‘저장/취소/완료’ 같은 버튼의 명사형은 정상이고 모두 문장으로 바꿀 필요가 없다. 가장 큰 문제는 말투보다 **현재 동작과 다른 약속, 결과가 모호한 동사, 오류 후 할 일의 부재**다. 아래는 변경을 권하는 것만 모았다. 제안 문구는 미구현이다. 조건부 제안은 동작을 먼저 맞춰야 한다.

## 덜어낼 것과 건드리지 말 것

**덜어낼 후보:** 목록의 미룬 횟수, 상태명을 다시 설명하는 긴 반복 안내, 여러 화면의 중복 숨김 설명, 모호한 삭제/넘기기 표현, 사용자가 직접 원본을 고치게 하는 설치 안내. 기능을 지우기보다 입력/복구 결과를 정확히 보여 주면 줄일 수 있는 문장들이다. 기록을 남기는 ‘안 함’, 수동 반복 옵션, 날짜 없는 할 일은 서로 다른 실제 의도가 있어 성급히 합치지 않는다.

**유지할 것:** 빠른 입력+해석 미리보기, 3개 탭, 폰 3일 시간표/PC 7일 보기, 겹침 목록, 체크할 일과 고정 일정의 분리, 본문 폭·여백, baseline에 신경 쓴 날짜/소분류, 별도 dark 토큰, 값이 있으면 펼치는 편집, 휴지통, 백업 파일, 기존 UID를 유지하는 비밀번호 재설정, 무채색 중심의 시각 질서. 한 사람용 앱에 협업·공개 가입·통계 대시보드·AI 자동 분류를 얹을 이유는 찾지 못했다.

## 앞선 두 검토와 다른 점

- 앞선 Codex가 지적한 로그인 복구 경로 부재, 검색 부재, 넘기기의 복사본 모델은 현재 상태로 재평가해야 한다. 2.5.0에서 이미 바뀐 문제를 계속 열린 문제처럼 세지 않았다. 처음 쓰는 타인의 이해보다 주인 한 명의 반복 사용을 더 무겁게 봤다.
- Claude U2의 날짜 이동에는 동의하지만 ‘N번 미룸’ 칩을 기본 표시하는 것에는 이견이 있다. 기록을 남기는 것과 늘 보여 주는 것은 별개다.
- Claude U3의 자동 추가 기본 켬에는 새 반복 기준으로 동의한다. 다만 자동 생성 시점/오프라인/알림의 정확한 약속과 기존 template 전환은 따로 다뤄야 한다.
- Claude U4의 시간표 글자 크기 변경은 주인의 결정을 존중해 이번 제안에서 제외했다. 대비 개선은 글자 크기와 별개다.
- Claude U5의 편집 접기는 유지한다. 전부 다시 펼치는 대신 시간 입력 직후 알림만 드러내자는 쪽이다. U6의 토스트 의존은 휴지통으로 일부 좋아졌지만 실패/초안/추정 수정에는 남아 있다.
- HANDOFF의 ‘넘기기’ 용어에는 ‘날짜 옮기기’가 더 명확하다는 이견을 남긴다. 규칙을 몰래 바꾸지 않았고 이 문서는 변경 제안이다. 분홍 규칙은 c7 예외를 기록하는 편이 현실적이다.
