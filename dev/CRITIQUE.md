# 또박 독립 검토 — 2026-10-29

검토 기준 커밋: `0c83e3b` (2.4.0). 개인용·비용 0원·모바일/PC 동기화 PWA라는 목적을 기준으로 평가했다. AGENTS.md와 HANDOFF 전체, 빌드·테스트, UI/CSS, 저장소 어댑터, 묶기, 서비스 워커, 알림 클라이언트·Worker, Firestore 규칙을 확인했다. 실제 운영 계정과 데이터에는 접근하지 않았다.

## 판단

강점은 빠른 입력, 날짜별 실행, 시간표, 오프라인이라는 개인 사용 목적이 분명하다는 것이다. 바닐라 JS 자체는 문제도, 프레임워크로 바꿔야 할 이유도 아니다. 메모리 저장소를 주입할 수 있는 경계와 알림 암호문까지 확인하는 테스트는 유지할 가치가 있다.

약점은 기능 개수보다 **사용자가 보는 상태와 실제 데이터 처리 사이의 신뢰**다. 백업 복원은 성공 표시와 달리 일부를 버릴 수 있고, 동기화·묶기·알림에는 실패/동시성 경계를 사용자나 테스트가 충분히 확인하지 않는 부분이 있다. 지금은 새 기능보다 이 경계를 단단히 하는 편이 낫다.

세 관점은 한 검토자가 각각 따로 적용했다. 여러 전문가나 실제 신규 사용자를 모집한 연구 결과는 아니다.

## 세 관점의 Critique

### 시니어 엔지니어·리뷰어

- 현재 가장 중요한 불변식은 “확인한 데이터를 쓴다”, “성공이라고 말할 때 무엇이 성공했는지 명확하다”다. 이번 변경은 이 중 백업 확인 경계와 목록 한도만 다룬다.
- 입력 정규화가 방어적으로 존재하지만 백업의 ID 필터링·중복 ID, 문자열 길이 제한, 날짜/시간의 정규식만 검사하는 문제는 남는다. 예를 들어 모양만 맞는 `99:99`는 의미상 유효하지 않다. 모든 과거 데이터 형식까지 조사하지 않고 엄격한 새 스키마를 한 번에 강제하면 정상 백업을 막을 수 있으므로 후속 과제로 둔다.
- `.catch(fail)`이 저장 실패를 UI 통지 후 resolve로 바꾸는 곳이 있다. “로컬 반영”, “서버 확인”, “실패/재시도”를 구분하는 계약이 필요하다. 오프라인 Firestore 쓰기의 대기 특성을 고려해야 하므로 전역 await 추가로 고치지 않는다.
- 보안 규칙은 UID 소유권 경계가 명확하다. 다만 소유권 검사는 문서 형식/크기 제한 검사가 아니다. 에뮬레이터 테스트 없는 규칙 강화는 지금 범위를 벗어난다.
- 프런트엔드에서 알림을 향후 62일·300개까지만 예약하므로 오랫동안 앱을 안 열거나 일정이 많으면 보장 범위가 달라진다. “알림을 켰다”와 “이 일정까지 예약됐다”를 구분해서 설명할 필요가 있다. 개인용이고 매일 앱을 여는 사용자라면 거대한 서버 스케줄러는 과잉이다.

### UX/UI·프로덕트 디자이너

- 휴대폰 390px와 PC 1280px에서 달력·전체·시간표·편집·백업 화면을 실행하고 스크린샷을 검토했다. 여백, 회색 기반, 주요 동작만 핑크로 표시하는 규칙은 유지할 만하다. 장식 변경은 우선순위가 낮다.
- 편집 시트는 날짜·시각·소요 시간·반복·세부 항목·메모·삭제·넘기기를 한 번에 드러낸다. 파워 유저에게는 효율적이지만 처음 쓰는 사람에게는 “단순 할 일”의 비용이 높다. 사용 빈도가 낮은 세부 설정을 접는 설계를 프로토타입으로 비교하자. 기존 사용자의 조작 횟수를 늘리는 변경은 사용성 확인 후 결정한다.
- ‘반복 할 일’은 실제 기록으로 추가해야 하고 ‘고정 일정’은 자체 발생한다. 다른 모델을 유지할 이유는 있지만 이름만으로 차이를 알기 어렵다. 최초 생성 위치에서 “자동으로 시간표에 표시”와 “그날 할 일로 추가해서 사용”을 짧게 설명하는 편이 새로운 탭 추가보다 낫다.
- 백업 텍스트는 현재 저렴한 이식 수단이지만 모바일 긴 텍스트 복사는 실수하기 쉽다. 파일 다운로드/파일 선택, 만든 시각·건수·복원 전 백업 안내가 다음 개선 후보이다. 별도 클라우드 백업 서비스나 비용을 추가할 필요는 없다.
- 색 외의 구분(이름·체크·텍스트)이 이미 있는 점은 좋다. 작은 회색 메타 글씨와 포커스 대비는 실측 감사, 터치 영역은 실제 기기에서 확인해야 한다. 이번 검토로 WCAG 준수를 인증하지 않는다.

### 처음 사용하는 사람의 관점 (시뮬레이션)

- 처음 빈 화면에서 카테고리의 +와 자연어 입력 예시는 이해를 돕는다. 반면 더보기 안의 두 반복 모델·알림 설정은 둘러봐야 발견할 수 있다.
- 로그인 화면에는 기존 계정 사용자를 위한 목적은 보이지만 계정 준비/비밀번호 복구 경로가 없다. 개인용 서비스에서 공개 회원가입을 여는 것은 방향 변경이므로 제안하지 않는다. 계정 안내와 분실 시 복구 절차를 사용자 문서에 연결하는 정도가 적절하다.
- ‘넘기기’의 “다른 날에 새로 추가”는 이동과 다르다. 기존 기록이 남는 의도는 설명되지만 동일 제목의 두 기록을 처음 보면 중복으로 느낄 수 있다. 실제 사용자가 구분할 수 있는지 과업 테스트가 필요하다.
- ‘숨김’은 삭제가 아니며, 카테고리를 숨기면 그 안의 일정도 보이지 않는다. 처음 사용하는 사람에게 빈 화면이 “자료가 없다”로 보이지 않도록 숨김 개수/복구 위치의 발견성을 검토하자.
